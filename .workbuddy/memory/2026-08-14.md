## mobile2: 重新加 react-native-safe-area-context（中午 11:31）

### 用户反馈
- 红屏 `Can't find ViewManager 'RNCSafeAreaProvider' nor 'RCTRNCSafeAreaProvider'`
- 提示设备在 USB/同 Wi-Fi + bundler=localhost:8081 时连不上 Metro

### 根因（重要的认知校正）
- 之前 2026-08-13 决定 **"mobile2 整个项目不引 react-native-safe-area-context"** — 这个决策是错的
- 真正的事实是 **react-native-screens 内部依赖 safe-area-context**：
  - `node_modules/react-native-screens/src/native-stack/views/NativeStackView.tsx:28-30` 直接 `import { useSafeAreaFrame, useSafeAreaInsets } from 'react-native-safe-area-context'`
  - `node_modules/react-native-screens/src/native-stack/utils/SafeAreaProviderCompat.tsx` 内部用 `<SafeAreaProvider>`
  - `@react-navigation/native-stack@7.x` peer dep 写 `react-native-safe-area-context: ">= 4.0.0"`（**写错了** —— 是 native-stack 的朋友，不是它的朋友；它的朋友其实是 screens 包的内部依赖）
- 所以 `App.tsx` 不引 `SafeAreaProvider` ≠ 项目能跑 —— native-stack 自己会引，缺包就崩
- 8/13 当时"卸载后用 RN 内置 StatusBar 铺底"那条决策的**逻辑**对（移除 SafeAreaProvider，简化 root 视图层级），但**结论**错：不应该卸载包本身，而是**保留包 + 不显式包 `<SafeAreaProvider>`**

### 修复
1. `apps/mobile2/package.json` 重新加 `"react-native-safe-area-context": "^5.6.2"` 到 dependencies
2. `pnpm install`（mobile2 子项目拿到 symlink 指向 `react-native-safe-area-context@5.6.2`）
3. `cd android && ./gradlew assembleDebug --no-daemon` 重新 build → BUILD SUCCESSFUL in 48s
4. APK 重新装到手机 + 启动 → MainActivity 焦点正常，无 bundle 错误，无 RNCSafeArea 红屏

### 关键教训
- **react-native-screens 依赖 react-native-safe-area-context**（hard internal import，不是 optional peer）
- 任何用 `@react-navigation/native-stack` 或 `react-native-screens` 的 RN 项目**必须**装 `react-native-safe-area-context`，否则 native-stack 第一次 mount 就会红屏
- 之前 8/13 "卸载 safe-area" 决策需要重新评估 — **保留包，不引组件**，而不是卸载包
- App.tsx 的 root 用 `<View flex:1 backgroundColor=theme.colors.background>` 铺主题背景**依然正确**（不依赖 SafeArea），只是**不能卸载** native 包

### 推广
- **不要在 RN 0.81 + screens 4.x 项目里卸载 react-native-safe-area-context**，会立刻崩
- 如果想去掉 SafeAreaProvider 的 runtime 副作用（不能完全去掉 native bridge），目前没有干净的办法 —— 必须接受 native bridge 存在

## adb 看不到设备但 ioreg 能看到 USB（重要 debug 经验）

### 现象
- `adb devices` 空（或 `unauthorized`）
- `adb install` 报 `device not found`

### 根因
**adb server 缓存里 USB 设备的授权 token 失效了**。物理层 USB 完全正常，是软件层 adb daemon 状态错乱。

### 快速排查
```bash
# 1. 确认物理层 USB 正常
ioreg -p IOUSB -l | grep -iE "Xiaomi|Mi |POCO|Redmi|android|miphone|24072"

# 2. 看 USB 设备位置
ioreg -p IOUSB -l | grep -E "@.*<class IOUSBHostDevice" | grep -iE "Xiaomi|小米"
# 应该返回类似：
# +-o Xiaomi MIX Fold 4@03120000  <class IOUSBHostDevice, ...>

# 3. 重启 adb server
adb kill-server
sleep 1
adb start-server
sleep 2
adb devices
# 应该立刻显示设备 serial（不需要重新接 USB）
```

### 关键认知
- **USB 没断**：ioreg 能看到 → 物理层 OK
- **不要让用户拔插 USB**：徒劳，反而可能真的断
- `kill-server + start-server` 通常**立刻恢复**（无需重新授权，因为手机已 paired）

### 触发场景
- 之前会话末尾做过 `adb uninstall` / `pm install` 卸载安装 APK
- adb daemon 状态错乱（少见）
- 长时间不用 adb 后第一次调用（小米 MIUI/HyperOS 偶尔会重置 adb USB authorization）

### 推广（写到这里：用户工作流）
- 排查 USB 看不到设备**永远先 ioreg**，再决定要不要重启 adb server

- 不会用 `/assets/<project_relative_path>` 简单拼接

- 所以 RN 项目里**项目根下放 `assets/` 子目录**会被识别成 `httpServerLocation: "/assets/..."`（相对 projectRoot 的 `/assets/` 是 path）

P3 复刻 mobile ReaderScreen 时 1:1 保留 mobile 旧版结构

   - bar 自己不接收触摸（避免误捕获），子组件（TouchableOpacity）正常接收

### 缺这两件时会发生什么

## pnpm patch 格式铁律（2026-08-14 17:38 关键教训）
**症状**：`ERR_PNPM_INVALID_PATCH Applying patch "react-native-webview.patch" failed: hunk header integrity check failed`
**根因**：旧 patch 文件用了 git format-patch 风格的 `index 0000000..0000001 100644` + `diff --git a/... b/...` 三行开头，pnpm apply 工具**不接受**这种格式，只接受**标准 unified diff 格式**：
```
--- a/<path>
+++ b/<path>
@@ -LINE,COUNT +LINE,COUNT @@
 ...context...
-removed
+added
 ...context...
```
**生成 patch 的标准流程（不要再用 Write 手写）**：
1. `curl -sL https://registry.npmjs.org/<pkg>/-/<pkg>-<ver>.tgz -o /tmp/x.tgz`
2. `tar -xzf /tmp/x.tgz -C /tmp/orig`
3. `cp -r /tmp/orig/package /tmp/patched` + 用 Edit 工具改 patched 文件加修复
4. `/usr/bin/diff -u /tmp/orig/package/.../file /tmp/patched/.../file > patches/<pkg>.patch`
5. macOS 默认 `diff` 不支持 `-u`（BSD diff），必须用绝对路径 `/usr/bin/diff`
**绝对不要**：
- 用 `Write` 工具手写 patch 文件（即使内容看起来对，格式差一点 pnpm 会拒）
- 用 `pnpm patch <pkg>` 命令（sandbox 杀 SIGKILL，exit 137 走不通）
- patch 文件保留 git format-patch 风格的 `index` 行
**触发场景**：mobile2 + react-native-webview@13.12.5 Kotlin null-safety 编译错（`RNCWebViewManagerImpl.kt:348` `String?` → `String`）。已修好 + patch 永久登记在 `patches/react-native-webview.patch` + `pnpm-workspace.yaml` 注册。
- `fontSize: 14` 太小（默认 17sp），可读性变差；用户说"看不到"= 14 字 + 64dp toolbar + 内部 padding 三者叠加超出可视区

### 修复（回滚 #1 #2，保留 #3 #4）
```diff
- ...Platform.select({
-   android: { height: 48 },
- }),
- headerTitleStyle: {
-   fontWeight: '600',
-   fontSize: fontSizes.md,
- },
+ headerTitleStyle: {
+   fontWeight: '600',
+ },
```
保留 `headerShadowVisible: false` + 4 项 border/shadow/elevation 0 —— **用户原始需求"去掉底边框/阴影"完全达成**。

### 用户实际要的"标题栏高度过高"的真问题
**回滚后用户可能仍嫌默认 64dp 偏高**。但 mobile 原版（expo 上跑的）同样是默认 64dp 没动过 —— 也就是说**用户过去在 mobile 上没觉得默认 64dp 过高**。
mobile2 上感觉偏高，可能是：
1. mobile2 status bar 没占空间（默认 24dp status bar 没让给内容），整体顶部 padding 多了 ≈ 24dp → 视觉感觉"高"
2. mobile2 用了 `edgeToEdgeEnabled=true` 之后 status bar 透明重叠内容，header 第一行按钮被压到状态栏区域

这两个都是 status bar / edge-to-edge 配置引起，不是 native header 本身高度问题。

### 教训（重要，推广）
1. **react-navigation native header 不能直接改 `headerStyle.height`** —— RN 库不接受，要改 header 高度只能用 `headerLargeTitle` (native-stack) 或自绘 `header: () => <CustomHeader />`
2. **改 native header 字号不能小于 16**（14 在 64dp toolbar 内部 padding 算下来会被剪切），最小安全值 16
3. **调试 native header 改动的"金标准"**：
   - `headerShadowVisible: false` 单独验证（保留）
   - `headerStyle: { borderBottomWidth: 0, shadowOpacity: 0, elevation: 0 }` 单独验证（保留）
   - **不要顺手改 height / fontSize** —— 这俩是另外的 request，用户没要求
4. **接到"高度过高"的需求要细问**：是 header 本身太高，还是第一行内容被状态栏遮挡？两种完全不同的根因 —— 之前 16:10 我猜 "height 太高"，猜错了就过头了
5. **永远保留用户明确要求的核心字段，只回滚过度添加的字段**

## mobile2: 再压 Tab header — height 64→56dp（16:14）

### 用户反馈

### 修订方案（不再过头）
把 `headerStyle.height` 加回，但用更保守的值：
- `android: { height: 56 }` ← Material 标准 compact header（不是 48dp 的极端值）

### 为什么 56dp 比之前 48dp 安全
- 64dp = Android native header 默认（Material standard medium）
- 56dp = Material 标准 compact header（很多 Android app 实际用的）
- 48dp = 触发 toolbar 内部 layout 让 17sp 字号没空间 padding，被压扁"看不到标题"
- **56dp 是 17sp 默认字号的最小可用值**（toolbar 内部 paddingVertical 还能容纳 17sp 不被剪）

`MainTabNavigator.tsx` headerStyle 加 `Platform.select({ android: { height: 56 } })`，fontSize 不动保留默认 17。

### 验证
- ✅ tsc 干净
- 等用户 reload 看效果
- 如果还嫌高，下一轮降手段：
  1. `header: () => null` 把 native header 完全去掉，三个 page 各加 30 行自绘 header（40-48dp）
  2. 不推荐轻易用 — 改 3 个 page 工作量大

### 教训（推广）
- **Android material header 标准高度梯度**：64dp / 56dp / 48dp（依次 compact），**字号 ≥ 17sp 时最低 56dp**
- **16:10 → 16:13 → 16:14 这个回合教训**：用户嫌高时减 8dp 是一档，每档都要单独验证；不要一步从 64 跨到 48（缺中间档 56），缺过渡一次过头一次回滚

## apps/mobile2 → apps/mobile 改名后清缓存铁律（2026-08-14 17:50）
**症状**：rename 后跑 `./gradlew assembleDebug` 报 21 个 native module 都 `No variants exist`（`No matching variant ... - No variants exist`）
**根因**：CMake 中间产物缓存（`apps/mobile/android/app/.cxx/`）**硬编码引用旧路径** `apps/mobile2/android/app/build/generated/autolinking/...`，路径找不到 → autolinking 生成的 native 源文件全 miss
**修复**：删 4 个缓存目录后重 build
```bash
rm -rf apps/mobile/android/app/.cxx          # CMake 中间产物(含旧 mobile2 路径)
rm -rf apps/mobile/android/app/build         # gradle 模块 cache
rm -rf apps/mobile/android/build             # project root cache
rm -rf apps/mobile/android/.gradle           # gradle 8.x metadata cache
./gradlew clean assembleDebug
```
**教训**：`mobile2 → mobile` rename 这种**物理路径改动**不只是 `mv`，必须连带清 **CMake `.cxx/`**（最容易被忽略，gradle 不会自动检测路径变化）。

## RN 0.81 Android 必须限定 ABI（2026-08-14 17:54）
**症状**：默认 ABI 编译时 `buildCMakeDebug[armeabi-v7a]` 失败，`ninja: ... failed while executing ... react_codegen_*` 多个 codegen 模块链接失败，log 截断到 [32/117] 后直接挂（**典型 OOM** 或 codegen C++ 在 32 位编错）
**根因**：RN 0.81 默认编译 4 个 ABI（arm64-v8a + armeabi-v7a + x86 + x86_64），32 位 codegen C++ 体量大、debug 构建编译慢、容易 OOM
**永久修复**（已加进 `apps/mobile/android/app/build.gradle` `defaultConfig.ndk`）：
```gradle
ndk {
    abiFilters "arm64-v8a"   // 仅 64-bit ARM,设备主流架构
}
```
**临时方案**（gradle property）：`./gradlew assembleDebug -PreactNativeArchitectures=arm64-v8a`
**APK 体积对比**：4 ABI = 204MB；arm64-v8a 单 ABI = 65MB（缩小 3 倍）
**什么时候加 x86_64**：要上 Play Store 时再加（emulator / Chromebook / ChromeOS），日常设备测试 arm64-v8a 就够了。
